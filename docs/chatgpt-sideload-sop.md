# ChatGPT Sideload SOP

## Purpose

This SOP lets an ordinary ChatGPT session with GitHub access perform narrow,
reviewable repository maintenance when Codex is unavailable. It is an intake
and small-correction lane, not a substitute for Codex architecture, research
promotion, validation, or release work.

## Repository architecture

- Static app: `index.html`, `app.js`, `styles.css`
- Canonical app data: `stores.json`, `events.json`, `sources.json`,
  `changes.json`
- Research record and methods: `research/`, including dated `research/runs/`
- Project direction and backlogs: `docs/`, `CURRENT_FRONTIER.md`
- Wizards crawler: `crawler/wizards_locator.py`, with dependencies in
  `requirements.txt`
- Generated/raw Wizards snapshot: `output/wizards/*`
- Deployment: `.github/workflows/deploy-pages.yml` publishes the static app and
  four canonical JSON files to GitHub Pages after pushes to `main` or
  `codex/reconcile-wizards`

`output/wizards/*` is generated evidence and must never be manually edited.
The GitHub Pages artifact is generated by the workflow and is not a canonical
editing surface.

## Safe edit scope

ChatGPT may:

- correct a clearly erroneous field on an existing record in `stores.json`,
  `events.json`, or `sources.json` when a cited source supports the correction;
- update an existing source's URL, label, check date, or documented status;
- add a source record for an already-existing canonical entity when the source
  is unambiguous and existing ID/type conventions can be followed exactly;
- add or refine research notes in `research/runs/` without claiming that a
  candidate has been promoted into canonical data;
- add documentary findings, feature ideas, ambiguities, and candidate
  discoveries to `docs/ASYNC_INTAKE.md`;
- exchange handoff messages in `docs/agent-mailbox.md`;
- maintain `docs/chatgpt-changelog.md` and purely documentary files.

These permissions are intentionally narrow. If an edit changes meaning beyond
a small correction, queue it for Codex.

## Prohibited without Codex

ChatGPT must not:

- create a new canonical store, venue, group, event, event series, or other
  entity; new discoveries go to `docs/ASYNC_INTAKE.md` as candidates;
- invent, rename, or migrate schema fields, enums, statuses, or ID conventions;
- change `index.html`, `app.js`, `styles.css`, crawler/parser/normalizer code,
  dependencies, workflows, deployment configuration, or agent automation;
- manually edit `output/wizards/*` or any generated deployment artifact;
- perform bulk rewrites, whole-file reformatting, mass normalization, or broad
  search-and-replace operations;
- delete records or silently remove stale information;
- promote speculative findings into canonical data;
- merge its own pull request or push directly to `main` without express user
  authorization.

## Required workflow

1. Read `AGENTS.md`, this SOP, `docs/agent-mailbox.md`, and
   `docs/ASYNC_INTAKE.md`.
2. Inspect the relevant record and nearby records before proposing an edit.
3. Identify the canonical file. Do not treat a screenshot, generated file, run
   note, or mailbox entry as canonical data.
4. Decide whether the request is safe, queue-only, or Codex-only.
5. For a safe edit, make the smallest possible diff. Preserve IDs, ordering,
   indentation, date/time/timezone conventions, enums, and surrounding style.
6. Do not invent missing values. Preserve an empty or unknown value using the
   convention already present in that file.
7. Cite source support in a run note, intake entry, or changelog entry.
8. Update `docs/chatgpt-changelog.md` in the same branch.
9. Prefer a branch named
   `chatgpt-data-update/YYYY-MM-DD-short-description` and open a pull request.
10. Report exactly what validation was and was not performed. Never imply that
    GitHub-only inspection is equivalent to a local app test.

## GitHub connector recovery checklist

If GitHub returns `403 Resource not accessible by integration`, or the session
cannot create a branch, commit, or pull request:

1. Stop the current write attempt. Do not fall back to editing `main`, an
   existing Codex branch, or any canonical file directly.
2. Check whether the ChatGPT GitHub plugin is merely connected or is actually
   installed for the repository.
3. If the plugin is not installed, use the ChatGPT plugin settings flow:
   - open the GitHub plugin page;
   - choose `Install plugin` if shown;
   - continue to GitHub;
   - install `ChatGPT Codex Connector` on the `metavirus` account;
   - grant `All repositories` access, or explicitly include
     `mtg-events-chatgpt`;
   - confirm that GitHub shows read and write access to code, pull requests,
     issues, actions, and workflows.
4. Confirm installation on the repository page:
   - `mtg-events-chatgpt -> Settings -> GitHub Apps`
   - expect to see `ChatGPT Codex Connector` with a `Configure` button.
5. Retry one minimal write probe only:
   - create a new `chatgpt-data-update/...` branch from the requested base;
   - do not edit files or open a PR during the probe.
6. If that probe succeeds, resume normal guarded branch-and-PR workflow and
   note in `docs/chatgpt-changelog.md` that connector write access is working.
7. Only if the install/configure flow is complete and the minimal write probe
   still fails should ChatGPT fall back to read-only handoff mode.

## Read-only handoff mode

Use this only after the connector recovery checklist above has been attempted
or when the user explicitly prefers not to reconfigure the plugin.

1. Stop all repository write attempts.
2. Continue only with read-only inspection, analysis, and source gathering.
3. Return one self-contained **ChatGPT Sideload Handoff Packet** containing:
   - the request and recommended disposition;
   - exact files that would change;
   - proposed mailbox, intake, and changelog text;
   - source support;
   - validation performed and unavailable;
   - risks and the specific Codex action requested.
4. Do not represent proposed text as applied repository work.
5. Codex may later apply and audit the packet. Until then, the ChatGPT session
   remains read-only and no canonical state has changed.

This fallback is a contingency, not the default response, when connector setup
has not yet been fully established.

## Data integrity rules

- Every factual data change must be traceable to a source.
- Preserve existing IDs. Candidate discoveries do not receive canonical IDs.
- Search for name/address variants before proposing any new entity to avoid
  duplicates.
- Reuse only existing enum/status/type values.
- Preserve local date, ISO timestamp, recurrence, and timezone conventions.
- Separate confirmed facts, analyst interpretation, and user-provided notes.
- Keep attributed user observations attributed to the user.
- Do not delete stale records; use an existing inactive/stale/status mechanism
  only when its meaning is clear and source-supported.
- Preserve confidence and research-status language. Do not upgrade confidence
  merely because a second weak source repeats the first.
- A candidate store, venue, group, event, or series belongs in intake until
  Codex researches, deduplicates, and promotes it.

## Validation checklist

There is currently no package manifest, automated test suite, linter, or
dedicated schema validator. For canonical JSON edits, locally run:

```powershell
Get-Content stores.json -Raw | ConvertFrom-Json | Out-Null
Get-Content events.json -Raw | ConvertFrom-Json | Out-Null
Get-Content sources.json -Raw | ConvertFrom-Json | Out-Null
Get-Content changes.json -Raw | ConvertFrom-Json | Out-Null
```

For a browser smoke test:

```text
python -m http.server 8000
```

Then open `http://localhost:8000` and inspect the affected view. The Wizards
refresh command is documented for Codex/automation and is not ordinary
ChatGPT's validation step:

```text
python crawler/wizards_locator.py --radius-miles 25 --output output/wizards
```

ChatGPT in GitHub-only mode may be unable to run any of these commands. It must
state that limitation in the changelog and PR rather than guessing that the
change is valid.

## Helpful guardrail responses

When a request exceeds the safe lane, respond constructively:

- New entity: "I found a possible new store/event/group. Creating canonical
  records requires Codex deduplication and validation, so I queued it as a
  sourced candidate in `docs/ASYNC_INTAKE.md`."
- Code or schema: "This changes app behavior or data architecture and is
  Codex-only. I recorded the request, expected outcome, evidence, and open
  questions for the next Codex session."
- Ambiguous fact: "The sources conflict, so I preserved both claims in intake
  and marked the decision as unresolved rather than changing canonical data."
- No validation: "I made the narrow documentary/data edit, but this session
  could not run local validation. The exact unperformed checks are listed in
  the changelog and PR."
- Unsafe bulk request: "This would rewrite too much to audit safely. I split it
  into bounded intake items for Codex rather than editing the dataset."

## Codex audit checklist

- Read pending entries in `docs/chatgpt-changelog.md` and addressed messages in
  `docs/agent-mailbox.md`.
- Diff every listed file against its parent commit.
- Confirm the edit stayed within ChatGPT-safe scope.
- Validate all four canonical JSON files when any was touched.
- Check schema, IDs, enums, dates, ordering, and formatting conventions.
- Check for duplicate entities and near-duplicate names/addresses.
- Verify source support and the distinction between fact and analysis.
- Run the local browser smoke test when user-facing data changed.
- Fix or revert unsafe changes and record the result in the Codex Audit Log.
- Move completed intake items to `Resolved` and leave a concise disposition.
